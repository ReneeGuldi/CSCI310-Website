How I synced 8 players in a browser game with Socket.IO

The Last Signal started as a single-player Three.js shooter. Making it multiplayer meant every browser had to agree on where everyone was, many times a second, without flooding the network or letting anyone cheat. Here's how I approached it, with the actual code.

Update, November 20, 2026: Sections 1–4 describe the first multiplayer version, which synced where players were but not the world itself, so everyone was fighting their own copy of the husks. I've since made the game truly co-op. Section 5 covers how.

The setup

Each player runs the full game in their own browser: the physics, the husks, the shooting. What they need from everyone else is much smaller: where each other player is and which way they're facing. So the server's main job is to collect those positions and pass them around.

The server is a small Node.js app using Socket.IO, which lets each side send named events:

// one side
socket.emit('state', data);

// the other side
socket.on('state', (data) => { ... });

That leaves three decisions: how often to send, how to make movement look smooth, and how much to trust what the browser sends.

1. Send at a fixed rate, not every frame

A game loop runs about 60 times a second. Sending your position on every frame means 60 messages a second per player, and with 8 players that adds up fast. It's also wasteful: nobody can tell the difference between 60 updates and 15 when they're watching someone else walk.

So the client keeps a small countdown timer and only sends when it runs out:

const SEND_RATE = 15; // updates per second

export function sendState(dt, position, rotY) {
    if (!isOpen()) return;
    sendTimer -= dt;
    if (sendTimer > 0) return;      // not time yet
    sendTimer = 1 / SEND_RATE;
    socket.emit('state', {
        x: +position.x.toFixed(2),
        y: +position.y.toFixed(2),
        z: +position.z.toFixed(2),
        rotY: +rotY.toFixed(3),
    });
}

The toFixed calls are a small detail I like: positions to the nearest centimeter are plenty, and rounding makes every message shorter.

2. Batch on the server: one snapshot, 20 times a second

The obvious first idea is a relay: whenever player A sends a position, forward it to everyone else. The problem is that the number of messages grows with every player who joins. With 8 players each sending 15 updates a second, the server would be forwarding hundreds of separate messages a second.

Instead, the server just stores each player's latest position when it arrives. Then, on its own fixed "tick," it sends everyone a single combined list: 

const TICK_RATE = 20;
setInterval(() => {
    for (const lobby of lobbies.values()) {
        if (lobby.players.size < 2) continue;   // nobody to sync with yet
        io.to(lobby.code).emit('snapshot', [...lobby.players.values()].map(publicInfo));
    }
}, 1000 / TICK_RATE);

Now each browser receives exactly 20 messages a second no matter how many people are playing. Since I added lobbies (one server, many separate games with join codes), the server loops over each game and uses Socket.IO rooms (io.to(lobby.code)) so a snapshot only goes to players in that lobby. A lobby with one lonely player gets nothing at all.

3. Interpolate so nobody teleports

20 snapshots a second is far fewer than 60 frames a second. If the game just snapped each remote player to their newest position, they would visibly stutter. So when a snapshot arrives, the client doesn't move anyone. It only updates where they're heading: 

socket.on('snapshot', (list) => {
    for (const p of list) {
        if (p.id === myId) continue;     // skip myself
        const r = remotes.get(p.id);
        r.target.set(p.x, p.y, p.z);
        r.targetRotY = p.rotY;
    }
});

Then, every frame, each remote player slides part of the way toward that target:

const t = Math.min(1, dt * 12);
r.root.position.lerp(r.target, t);

// turn the shortest way around
let diff = r.targetRotY - r.root.rotation.y;
diff = Math.atan2(Math.sin(diff), Math.cos(diff));
r.root.rotation.y += diff * t;

The rotation line fixed a funny bug. Angles wrap around, so turning from 170° to −170° is really a 20° turn, but subtracting the numbers says 340°. Without the atan2 trick, players would spin almost all the way around just to turn slightly left. Wrapping the difference into the range −180° to 180° always picks the short way.

4. Never trust the client

Anyone can open their browser's developer tools and send whatever they want to my server. So the server treats every message as untrusted. For position updates, it copies only the four fields it expects, and only if they're real numbers: 

socket.on('state', (msg) => {
    if (!msg) return;
    const s = player.state;
    for (const key of ['x', 'y', 'z', 'rotY']) {
        if (Number.isFinite(msg[key])) s[key] = msg[key];
    }
});

Extra fields are ignored, and junk like "hello" or NaN never reaches other players. The same idea applies elsewhere: player names are stripped down to safe characters and 16 characters max before anyone else sees them, the lobby caps at 8 players, and the file server blocks ../ tricks so nobody can read files outside the game folder.

5. Update: from side by side to truly co-op

Everything above makes players visible to each other. But in that first version, every browser still ran its own copy of the world: its own husks, its own radio parts, its own tower. You could watch a friend fight a husk that didn't exist in your game. You were playing next to each other, not with each other.

Sharing one world raises a hard question: if two players shoot the same husk at the same moment, whose game is right? My answer was to make one game the source of truth: the host's. The host's husks think and attack. Everyone else's husks are puppets that copy the host's 10 times a second: 

const HUSK_SEND_RATE = 10; // husk updates per second from the host

export function shareHusks(dt) {
    if (!inLobby() || !runsWorld()) return;   // only the host shares husks
    huskTimer -= dt;
    if (huskTimer > 0) return;
    huskTimer = 1 / HUSK_SEND_RATE;
    sendWorld('husks', huskSnapshot());
}

That means a teammate can't just kill a husk on their own screen. When they shoot one, their game shows the hit, then sends the host a request: 

if (h.puppet) {
    // not our husk: show the hit, and tell the host so it takes the damage
    flashRed(h.mesh);
    sendWorld('hit', { id: h.id, amount, dx: dir.x, dz: dir.z, force }, 'host');
    return;
}

The host applies the damage to the real husk, then reports back: points to whoever got the kill, damage to whoever got bitten, loot to everyone. The same pattern of "requests go to the host, results come back" covers shoves, nests, the evac barricade and gunfire noise. Shared events like picking up an item, opening a drawer or blowing up a barrel go to everyone, so the whole lobby works toward the same radio parts, the same tower and one win screen.

A few details made it hold together:

  • Late joiners catch up. When someone joins mid-run, the host sends them everything that already happened: parts found, nests destroyed, barrels blown and the tower's progress.
  • Host handoff. If the host leaves, the next host's puppet husks start thinking for themselves, and the run keeps going.
  • Still untrusted. The host clamps everything it receives. A hit request can't do more than 20 damage, no matter what a modified browser sends.
  • Solo still works. Playing alone, none of this runs: you're simply your own host.

What I'd do next

Right now the host's browser runs the world. That works well for friends playing together, but a player who controls the host could still bend the rules, and there's a brief hiccup when a host leaves. The next step would be moving the world onto the server itself. After that, client-side prediction would hide network delay on slow connections.

Takeaways

  • Pick rates on purpose. 15 updates up and 20 down was plenty for smooth play, and far cheaper than "every frame."
  • Batch on the server. One snapshot per tick keeps traffic predictable as players join.
  • Smooth on the client. Interpolation, with angle wrapping, does more for how it feels than a higher send rate would.
  • Validate everything. If it came from a browser, check it before you use it.
  • Pick one source of truth. A shared world needs exactly one game deciding what's real; everyone else sends requests and copies the result.
